# Agent Readiness Report

Evaluate the requested repository, or the current working directory. Read
[references/criteria.md](references/criteria.md) for the versioned rubric and
scoring rules. This is an independent oanastack assessment inspired by
[Factory's article](https://factory.com/news/agent-readiness), not a Factory
report or an implementation of its unpublished evaluator.

## Scope and data boundaries

- Apply the target repository's instructions and documented workflow. Do not
  carry conventions from the repository containing this skill into the target.
- Inspect locally by default. Do not invoke Factory, upload a repository or
  report, post issues, or query hosted services unless the user requests it.
  Public methodology links are attribution, not a runtime dependency.
- Local inspection does not mean offline model inference. The host agent may
  send inspected context to its configured model provider. Explain that boundary
  if the user asks about confidentiality; do not promise zero data transmission.
- Avoid opening credential files, dumping environment values, or printing
  sensitive remote URLs. Report configuration names and presence, not values.
- Return the report in the conversation. Save only when requested, to the
  requested destination; private findings do not belong in oanastack's source.
- Assessment does not authorize repairs, dependency installation, submodule
  initialization, hooks installation, service startup, releases, or commits.

## Evaluation workflow

1. Establish scope: repository revision and dirty state, application boundaries,
   languages, package managers, and the requested static or executable checks.
   For a monorepo, identify independently deployable apps; treat shared packages
   as supporting modules rather than inventing extra apps to inflate the score.
2. Read repository instructions, setup docs, build/test recipes, CI definitions,
   environment templates, and relevant source. Prefer targeted file discovery.
   Follow the actual recipe behind a command before executing it.
3. Evaluate every rubric ID. Use `pass`, `fail`, `unknown`, `blocked`, or `n/a`;
   attach a file/line, an observed command result, or an authorized external
   observation. Separate repository scope from each applicable application's
   results. Equivalent mechanisms count; tool brand and hosting vendor do not.
4. Run a small representative set of existing checks when dependencies and
   prerequisites are ready. Detect package-manager auto-install behavior before
   invocation. Commands that fetch dependencies, start services, write persistent
   data, or target shared environments need their own authorization. Run dependent
   setup and checks sequentially; do not race installs. If prerequisites are
   missing, record the block and continue static inspection.
5. Compute the conservative maturity result using the rubric. Prioritize three
   to five improvements by the failure they prevent and their effort. Describe
   a concrete verification command or observable acceptance condition for each.
   Do not fix findings as part of the report.

Stop when all rubric IDs have evidence or an explicit uncertainty, representative
checks have results or blockers, and the highest-impact next actions are clear.
Do not run the entire test suite solely to improve an assessment score.

## Report contract

Write in the user's language. Lead with the practical conclusion and whether
the result is verified or provisional. Include:

- Scope, revision/dirty state, rubric version, applications, and checks performed.
- An eight-pillar summary, then a compact criterion table: ID, scope/application,
  status, evidence, and gap. Label evidence `static`, `executed`, or `external`.
- Per-level counts and maturity result; do not present an oanastack score as
  Factory's score. Unknowns and blockers remain visible, not silently excluded.
- Prioritized actions with impact, effort, and verification; command failures,
  skipped checks and their reasons; any files generated by executed checks.

Use repository-relative paths in saved reports for portability. Resolve clickable
links appropriately in the host UI. Do not reproduce secrets, proprietary source
snippets, personal paths, internal domains, or raw logs in public examples.

For repeat assessments, reuse the same rubric and application boundaries, compare
evidence with the previous report, and explain score changes. Previous outcomes
are context, never evidence that a criterion still passes.
