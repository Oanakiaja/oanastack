# 原则

动手前读完。引用一条时，写出它改了哪一个决定。这里是判断。步骤仍在 playbook。本文件不新增路由，也不复制 pstack 的原则清单。

思想来自 poteto / pstack 的近期做法，按 oanastack 已有骨干改写。Comment Sicko 的人格和脚本不引入。

## 工作单元可以验证

- 以 feature 为最小可交付单元。每一步的结尾是一次能失败的检查。
- 多仓协作时使用隔离 worktree，避免污染主 checkout，也避免上下文混在一起。

## 够用，并且能被证伪

好代码的次序是：够用，能被证伪，然后才是看起来干净。

- **够用。** 改动只覆盖目标要求的行为。
- **能被证伪。** 有一条检查。它失败时指出行为错了。编译通过、lint 绿、「看起来对」都不是这条检查。
- **看起来干净排在后面。** 为了干净加上的抽象、叙述性注释和代理检查是成本。下一份 diff 更长，也更难证明。
- **所有代码先按 slop 对待。** 生成的和手写的一样。作者是谁不改变这个次序。够用和能被证伪都站住之后，这段代码才可以留下。

## 工程师掌握解药

指出 slop 不改变 diff。解药由写这段代码的工程师负责，三选一：

1. 对准真实行为的检查。
2. 删掉绕路。
3. 让这类错误无法再写出来的结构（类型、lint、测试）。散文守则排在这三者后面。

模型不会替这份 diff 长出判断。未验证就合入，是工程师的决定。

## 写下来才算想清楚

编码前用自己的话写下四样：目标、底下的问题、正在假设什么、还不确定什么。写这一段就是在对齐意图。复述和用户要的对不上，停在复述，先不要改代码。

用户对原因的猜测记成假设。证据已经否定它时，写出那份证据。复述可以重复用户已经给出的修法，这里不另起一套计划。

句子怎么写，交给技术写作卡（草案在 [#11](https://github.com/Oanakiaja/oanastack/pull/11)）。本节约定的是写的时机。`feat` / `bugfix` / `research` 上的复述步骤见 `poteto-fold.md`，尚未写进那些 playbook。

## 注释是病毒

优先删。最会传染的是临时 workaround 笔记：`for now`、`TODO 以后再删`、`先这样`、`别改这段`、`测试不稳定所以跳过`。下一任 Agent 会把这些句子抄成约束，绕路就留下了。

删注释时一并处理它保护的绕路。只删句子、留下绕路，病毒还在。

留得下的注释只有一种：代码表达不了的原因，并且原因在我们改不了的外部（协议、平台、许可证、对外 API 合同）。拿不准就删。

不因这条去扫全仓，本文件也不规定 lint。`code-style.md`（草案在 [#6](https://github.com/Oanakiaja/oanastack/pull/6)）里的「注释只写非显然的 why」要指回上面的保留清单，两处说同一件事。

## 同一类错误第三次才成为标准

一次纠正是教训：规则、为什么、证据、见到的场合。同一类在三个分开的场合再出现，才升级成标准。一个 diff 里写三遍算一个场合。计数沿用 [Magpie](https://github.com/yetone/magpie/blob/main/LESSONS.md) 的「不同日子」，热闹的一天不会变成法律。

升级写进已经负责这件事的 reference。能变成 lint、类型或测试的，不再加一段散文。计数步骤留在 `playbooks/reflect.md` 的后续改动里。现有的低 / 中 / 高门槛保持不变。
