# 技术写作

目标：累了的工程师第一遍就能读懂。四层各问一件事：这是哪种文档、句子怎么对着读者、一句装多少、会不会读出两种意思。四层都用。

## 总则

- 砍掉不起作用的词。拿掉它句子还活着，就拿掉。`in order to` 写成 `to`。`It is important to note that` 整段删。
- 用短的日常词：用 / 帮 / 做，不要 `utilize` / `facilitate` / `perform`。长词必须用精度换长度。
- 规则让句子变差就改写法，或先放下。规则为读者服务。句句合规却像机器写的，已经失败。
- 代码库是词表：写真实符号、路径、flag、命令，不要同义改写。
- 别造黑话。开发者会说出口的词才用。新黑话提议走 unslop 类规则，本卡不展开 slop 目录。

## 节奏

- 长短句混用。短句落地，长句带条件或后果。
- 一句一意 ≠ 一句一长。两意就拆，一意可留长。
- 模式允许时可以有观点：Explanation 权衡要表态；Reference 保持干。
- 具体好过空话：不写「改 schema 可能出问题」，写「重命名列会让构建失败」。

## 层 1：先定模式（Diátaxis）

一篇一种。两问：服务行动还是理解？服务学习还是干活？

| 行动？ | 学习 / 干活 | 模式 |
| --- | --- | --- |
| 行动 | 学习 | **Tutorial**（教程：跟着做来学） |
| 行动 | 干活 | **How-to**（操作指南：到达目标） |
| 理解 | 干活 | **Reference**（查阅：事实） |
| 理解 | 学习 | **Explanation**（解释：为什么） |

**Tutorial：** 你是老师，做成是你的责任。开篇说会做出什么，不说「将学到」。每步尽早有可见结果，告诉他们该看到什么。解释压成一句加链接。用「我们」+ 命令句。

**How-to：** 解决人的问题，不教课。默认读者会干活。只要动作，背景用链接。允许分叉：「想要 x，就做 y」。标题用任务：「如何校准雷达阵列」，不要「雷达阵列校准」。

**Reference：** 只描述。无指令、无劝说、无观点。干、全、肯定。事实 / 选项 / 限制 / 错误不打马虎眼。结构和被描述物对齐。能从代码生成就从代码生成。

**Explanation：** 一个有边界的主题，离开产品也能读。标题能在前面加上「关于…」。锚在真实的 why。给上下文：决策、历史、约束、替代。只有这里允许观点。

禁止混模式：Tutorial 里不塞对照表，Reference 里不手把手，How-to 里不辩论。拆开再链接。

来源：diataxis.fr

## 层 2：对着读者写（Google developer style）

- 用「你」，现在时。「会 / 将」只留给真的以后才发生的事。
- 说清谁做什么：「编译器检查」，不要「被检查」。被动只在不知道谁做、或谁做不重要时用。
- 指令用命令句：「点提交。」陈述事实。不要「应当被完成」。
- 条件在动作前：「要删除文档，点删除。」读者能跳过不适用的。
- 常见情况优先，例外放后面。
- 像懂行的同事。指令里不要「请」，流程里不要「简单 / 容易 / 很快」。真简单读者就不会来。
- 不要预告（「我们即将支持…」）；不要连续句用同一开头。
- 链接写目的地：页标题或短描述，不要「点击这里」。本页能说清就少链出去。
- 标题带观点，不只是话题（「先定模式」，不要「模式」）。标题用句子大小写。任务标题是动词短语，概念标题是名词短语。一页一个 h1，不跳级。
- 序列用编号，其余用项目符号。列表前用完整句。条目平行。
- 代码等宽，UI 加粗。用序列逗号。不要 `etc.`，事先说清单不完整。

来源：developers.google.com/style

## 层 3：一句装一件事（STE）

- 一句一指令；别处一句一意。
- 指令大约超过 20 词、其他句子大约超过 25 词就拆。
- 警告 / 条件在步骤前。
- 英文留 `the` / `a`：`Remove backup file` 有两种读法，`Remove the backup file` 只有一种。中文把对象写全，别省到两种读法。
- 一词一义、一词一职。`check` 如果是检查，就不要再当阻止用。
- 同一动作只用一个词：这里 `start`、那里 `initiate`，不行。
- 程序用命令句，不用叙述、不用被动：「安装该组件」，不要「该组件必须被安装」。
- 少用能兼多职的进行式 / 「着」。容易读岔。

来源：asd-ste100.org（Issue 9, 2025）

## 层 4：不给两种读法（Global English）

- `only` / `not` 贴紧被限定的词。「只在增长时失败」和「在增长时只失败」不是一回事。
- 拆名词串：`the proto import budget check script` 写成「检查 proto import 预算的脚本」。
- `it` / `they` / `this` 必须只指向一个明显的东西。拿不准就重复名词。不要用 `this` / `which` 指整句。
- 别丢动词。并列时每边都给动词。
- 留着标明结构的小词。清晰优先于字数。
- 并列时该重复的限定就重复：两件东西就都写全（`the client and the host`）。
- `and` / `or` 可能两种切法时，写清谁跟谁。`both…and` / `either…or` / `if…then` 能消歧就用。
- 用句号，少用分号。破折号改成新句子。
- 括号里是完整语法单位或另起一句。不要用 `(s)` 表示复数。
- 别用 `/` 和模糊 `and/or`：写成「a、b，或两者」。
- 一事一名，全文同一叫法。不要同一东西轮流叫闸门 / ratchet / 预算检查。
- 少成语、口语、拉丁缩写、隐喻。母语不是英语的人、翻译、Agent 都更容易解析平铺句。

来源：Kohl, *The Global English Style Guide*

## 仓库特例

- PR / commit 也是写作（除 Diátaxis 外都适用）。PR = 一分钟 briefing，别贴 swarm 日志 / SHA 表，用链接。
- 产品 UI 文案不是文档。UI 走产品自己的文案规范。
- 路径、符号、数量必须在落地 commit 为真；数量写上能复算的命令。

## 对照（可抄）

改前：

> proto import ratchet budget 脚本的参数配置通过 budget.json 执行。需要注意的是，带着 `--write` 跑（会把已提交预算更新为当前计数）应当只在降低它时做。如果超了，CI 会失败。

改后：

> `budget.mjs` 从 `budget.json` 读已提交预算，并统计 import proto 的文件数。计数超过预算时 CI 失败。只有要降低预算时才跑 `budget.mjs --write`。

## 审阅清单

用于本卡覆盖的正文。第 1 条只用于文档集：

1. 每个文件是一种 Diátaxis 模式吗？模式交接处有链接吗？
2. 每条指令都是命令句、条件在前吗？
3. 有没有一句装了两个指令或两层意思？拆开。
4. 有没有词拿掉也不损意？拿掉。
5. `only` 贴着它限定的词吗？每个「它」只指向一件事吗？每个从句都有动词吗？
6. 同一事物在文档里只有一个名字吗？
7. 开发者会把这些词说出口吗？黑话和花哨同义词换成白话或真实符号。
8. 符号、路径、数量在本 commit 都为真吗？数量附了复算命令吗？
